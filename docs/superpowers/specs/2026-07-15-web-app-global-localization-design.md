# 官网全局中英文本地化设计

## 背景

Oh My Prompt 官网目前仅订阅、联系和法律页面具备 `/en/...` 英文路由。首页、文档、认证、备份、控制台和团队页面仍只有中文版本。顶部导航栏同时展示“中文”和“English”两个入口，法律页面正文还存在第二套语言切换，交互不统一；部分中文页面切换英文后会进入不存在的路由。

本次改动将官网所有用户可见页面完整本地化为中文和英文，并将语言入口统一为顶部导航栏中的单一下拉菜单。浏览器扩展不在本次范围内。

## 目标与验收标准

- 所有用户可见页面均有中文和英文版本，包括首页、文档列表及全部文档正文、认证流程、备份、控制台、团队、订阅、联系和法律页面。
- 中文页面使用原路径，英文页面使用对应的 `/en/...` 路径。
- `/...` 始终默认为中文；不按浏览器语言自动跳转，不使用 Cookie 或本地存储覆盖 URL 所表达的语言。
- 顶部导航栏只保留一个语言下拉入口，触发器显示当前语言“中文”或“English”。
- 语言切换保持当前页面、动态参数和查询参数；不存在无效英文页面或中文内容静默回退。
- 用户可见的按钮、标签、校验提示、错误提示、空状态和页面元数据均随页面语言变化。
- 法律页面正文中的重复语言切换被移除。
- 现有认证、团队、同步和支付业务行为不因本地化而改变。

## 非目标

- 不修改浏览器扩展的语言切换。
- 不增加中英文以外的语言。
- 不根据地理位置或浏览器设置自动选择语言。
- 不翻译纯服务端日志、开发注释、测试夹具或不直接展示给用户的 API 内部错误。
- 不在本次工作中重构与本地化无关的页面或业务逻辑。

## 方案选择

采用现有路由模式：中文位于原路径，英文位于 `/en/...`，页面业务组件共享，通过类型化 `locale` 和集中式文案字典渲染不同语言。

未选择以下方案：

- `next-intl` 等完整国际化框架：会引入依赖、middleware 和更大范围的路由重构，超出当前中英文需求。
- Cookie 或本地存储驱动的同路径切换：URL 无法稳定表达语言，不利于服务端渲染、SEO 和链接分享。

## 路由设计

每个中文页面必须有对应英文路径：

| 中文路径 | 英文路径 |
| --- | --- |
| `/` | `/en` |
| `/docs` | `/en/docs` |
| `/docs/[slug]` | `/en/docs/[slug]` |
| `/auth/*` | `/en/auth/*` |
| `/backup` | `/en/backup` |
| `/dashboard` | `/en/dashboard` |
| `/team` | `/en/team` |
| `/team/join` | `/en/team/join` |
| `/team/[teamId]` | `/en/team/[teamId]` |
| `/subscription` | `/en/subscription` |
| `/contact` | `/en/contact` |
| `/privacy` | `/en/privacy` |
| `/refund` | `/en/refund` |
| `/terms` | `/en/terms` |

英文路由文件应保持轻量，只负责传入 `locale="en"` 和路由参数。页面布局、数据请求、表单提交和业务状态由中英文共享组件实现，避免复制业务逻辑。

语言切换函数负责添加或移除单个 `/en` 前缀，并原样保留动态路径和查询参数。认证成功、OAuth 回调、支付成功、团队邀请和其他重定向也必须携带当前语言上下文。

## 文案与内容架构

### 页面文案

建立集中、类型化的双语文案模块。按功能域拆分，例如 `layout`、`auth`、`dashboard`、`backup`、`team` 和 `billing`，避免单个超大字典。共享组件接收 `locale: 'zh' | 'en'`，并从对应功能域读取文案。

文案模块覆盖：

- 标题、正文、按钮和导航标签；
- 表单标签、占位符、帮助文本和校验信息；
- 加载、空状态、成功和失败反馈；
- 对话框、确认提示和无障碍标签；
- 页面 title、description、Open Graph 和 canonical/alternate 元数据。

服务端 API 可以继续返回稳定错误码。页面根据错误码和当前 `locale` 映射为用户可见文案，避免在业务接口中复制整套翻译。

### 文档内容

每篇中文文档必须有对应的英文正文，并保持相同 slug，确保 `/docs/[slug]` 与 `/en/docs/[slug]` 一一配对。文档索引根据 `locale` 读取对应标题、摘要和正文。

英文内容缺失时不回退中文。构建或测试应检查两种语言的文档集合和 slug 完全一致，并明确报告缺失项。

### 动态数据

用户、团队、提示词和账单记录等用户数据不翻译。固定状态名称、日期格式、金额说明和系统生成提示根据 `locale` 本地化。英文页面使用英语区域格式，中文页面使用中文区域格式。

## 顶部语言下拉

顶部导航栏中的原并排语言链接替换为单一下拉组件：

- 关闭状态显示当前语言全称和向下箭头；中文页显示“中文”，英文页显示“English”。
- 展开菜单包含“中文”和“English”两项，当前项带选中标记并设置正确的 `aria-current`。
- 菜单支持点击外部关闭、Escape 关闭、方向键移动和 Enter/Space 选择。
- 触发器和菜单项具有清晰的键盘焦点样式，并满足至少 44px 的触控尺寸。
- 切换后导航到当前页面的配对语言路径；当前语言项不触发多余导航。
- 移动端仍位于顶部导航栏操作区，不另设第二套切换入口。

法律页面标题区域中的 `LanguageMenu` 被移除，页面仅使用全局顶部下拉。

## 数据流

1. 路由决定当前 `locale`：无 `/en` 前缀为 `zh`，有 `/en` 前缀为 `en`。
2. 页面入口把 `locale` 传给共享页面组件。
3. 共享组件使用 `locale` 读取类型化文案和格式化规则。
4. 顶部语言下拉根据当前 pathname 和 search params 生成配对 URL。
5. 用户选择另一语言后执行普通 Next.js 导航；URL 成为语言状态的唯一来源。

## 错误处理与兼容性

- 语言 URL 生成器必须避免重复 `/en/en/...`，并正确处理根路径、动态段、尾斜杠和查询参数。
- 认证和业务 API 的稳定错误码在客户端按语言映射；未知错误使用对应语言的通用错误提示。
- 英文页面不允许因缺失字典键而回退中文。开发和测试阶段通过类型检查发现缺失键。
- 对没有可翻译内容的用户数据保持原值，避免改写用户输入。
- 现有中文链接保持不变，保证兼容已有收藏、搜索索引和外部引用。

## 测试策略

### 单元测试

- 配对路径转换：根路径、普通路径、动态路径、查询参数和 `/en` 前缀去重。
- 文案字典：中英文键结构一致，无缺失值或中文静默回退。
- 文档索引：两种语言 slug 集合完全一致，每篇文档均有英文正文。
- 错误码映射和日期/金额格式根据 `locale` 输出正确语言。

### 组件与端到端测试

- 顶部只出现一个语言触发器，法律页面不存在正文内的重复切换。
- 下拉显示当前语言、当前项标记正确，并可通过鼠标和键盘操作。
- 从每类页面切换语言后保持页面、动态参数和查询参数。
- 首页、文档、认证、备份、控制台、团队、订阅和法律页面的代表性英文路径可访问。
- 登录、注册、重置密码、OAuth 回调、团队邀请和支付流程在英文路径开始后保持英文上下文。
- 关键英文页面不包含遗留的固定中文界面文案。

### 回归验证

- 运行 Web App 单元测试、Playwright UI 测试、类型检查和生产构建。
- 保留现有支付、认证、团队和同步测试，确保本地化没有改变业务契约。

## 实施边界

实施按功能域逐步进行，每一步先增加失败测试，再完成最小代码使其通过。只修改官网本地化直接涉及的路由、组件、文案、文档和测试。若盘点中发现与本任务无关的历史问题，仅记录，不顺带重构。
